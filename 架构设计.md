# 通用 EVM Mint Engine — 架构设计

> 文档版本：v1.3  
> 使用与部署：[README.md](./README.md) · [部署.md](./部署.md)  
> 目标：构建一个可扩展的通用 EVM Mint Engine，用同一套框架处理 ERC-20、ERC-721、ERC-1155 以及不同项目的 Mint / Claim / Public Sale / Allowlist / Signature / SeaDrop 等发行模式。  
> 核心原则：**不要假设所有项目存在统一的 `mint()`；把“函数发现、参数推导、交易构造、签名、广播、确认”拆成独立模块。**  
> 实现已落地部分以 README 为准。文中「从地址自动检测链」已否决，链必须手选。阶段 chase：T−20 预分析/Gas、T−5 FINAL、ARMED 后热路径先 OpenSea `/mint` 并复用 TxPlan；公开轮 T−1 链上预签、到点 probe 后广播。无阶段 BLAST 仍为 T=0 边签边发。多 RPC 默认按延迟分片。预约时可选 PREPARE_LEAD；BLAST 前 probe_on_start 会再 probe 并重算分片。inspect 余额预留用 gas_limit×maxFee。

## 1. 项目目标

### 1.1 核心目标

输入一个合约地址后，系统尽可能自动完成：

```text
Contract Address
        ↓
Chain Detection
        ↓
Contract Type Detection
        ↓
ABI / Bytecode / Selector Analysis
        ↓
Mint Method Detection
        ↓
Parameter Detection
        ↓
Price / Limit / Time / Proof Detection
        ↓
Transaction Builder
        ↓
Pre-sign
        ↓
Multi-RPC Broadcast
        ↓
Receipt Monitoring
        ↓
Result Parser
```

目标不是实现“一个万能 mint 函数”，而是实现：

> **一个万能的 Mint 调度框架 + 多种 Mint Adapter。**

---

## 2. 设计原则

### 2.1 不依赖统一 Mint 标准

EVM 没有规定 NFT 或 ERC-20 必须存在：

```solidity
mint(uint256)
```

因此不能把 `mint(uint256)` 作为系统唯一入口。

系统应该同时识别：

```text
mint
publicMint
presale
publicSale
claim
purchase
buy
mintNFT
mintPublic
safeMint
airdrop
```

以及第三方发行协议，例如：

```text
SeaDrop
Manifold
ERC721A Sale Contract
Custom Mint Contract
Proxy / Router
```

---

### 2.2 ABI First，Selector Second

优先级：

```text
1. 用户手动输入的 ABI
2. 已知 / 本地缓存 ABI
3. 链上验证 ABI
4. Proxy Implementation ABI
5. Function Selector 数据库
6. Bytecode / Storage / Event 分析
7. 手工构造 calldata
```

有 ABI 就使用 ABI；没有 ABI 也不能直接判定“不支持”。

---

### 2.3 Read 和 Write 完全分离

Read 层只负责：

```text
价格
开始时间
结束时间
Wallet Limit
总供应量
剩余供应量
Merkle Root
Whitelist
Sale State
Contract Type
```

Write 层负责：

```text
Build Transaction
Sign Transaction
Broadcast Transaction
Monitor Receipt
```

# 19. ABI-less Mode

核心流程：

```text
没有 ABI
        ↓
Selector
        ↓
Function Signature
        ↓
Manual ABI Encoding
        ↓
Raw Transaction
```

例如：

```python
selector = Web3.keccak(
    text="mint(uint256)"
)[:4]
```

然后：

```python
encoded = eth_abi.encode(
    ["uint256"],
    [quantity],
)

calldata = selector + encoded
```

交易：

```python
tx = {
    "to": contract_address,
    "data": calldata,
    "value": value,
    ...
}
```

# 26. Gas Manager

支持：

```text
Legacy Gas
EIP-1559
```

EIP-1559：

```text
baseFee
priorityFee
maxFee
```

策略（与控制台默认一致：额外 tip=1、倍率=1）：

```text
maxPriorityFeePerGas = 链上 tip + extra_priority_gwei
maxFeePerGas         = baseFee * max_fee_multiplier + priority
```

`extra_priority_gwei ≤ 0` 不加额外 tip；`max_fee_multiplier ≤ 0` 当作 `1.0`。页面无硬顶。重试时 `priority × 1.5^attempt`，倍率再乘 `1.25^attempt`，gasLimit 沿用首次 estimate。

# 27. Gas Estimation

需要特别处理 Mint Start 前的情况。

因为：

```text
drop not active
```

此时：

```text
eth_estimateGas
```

可能直接 revert。

因此：

```text
构造交易时对真实 calldata 做 eth_estimateGas × 1.2
估失败（含开售前 NotActive）→ fallback 280000
SoldOut 类 revert → 立刻停未发送钱包，不换节点重试 estimate
T=0 每个钱包当场估 gas、签名并立刻广播，不再批量预签
重试加价不重估 limit
```

抢 Mint **不在 T-20 批量预签**。每个钱包到点后在自己的分片节点上估 gasLimit 并签名发送。

# 30. Multi-RPC Broadcast

支持自有 RPC 与公开节点。当前默认不是「同一笔齐射多个节点」：

```text
测速按延迟排序
并发数 = 每个节点同时飞行的钱包数
钱包按组切到最快的节点；一组满了再分给下一节点
同一笔 raw tx 默认只打该分片；429 才切更慢的下一个
broadcast_backups=true 时才对同一笔多 RPC 齐射
```

重要原则：

> **多个 RPC 广播同一个已签名交易，不会因此产生多笔链上交易。**

# 36. Retry Engine

不是所有错误都应该重试。

```text
RPC timeout
        → retry

SEND_FAILED / TIMEOUT（广播后）
        → 同 nonce 加价重签，次数由 max_retries 决定

NFT 归集（mint_engine/sweep）：
        预览只查持仓，不看目标地址
        优先 tokensOfOwner / walletOfOwner
        再 Enumerable / 浏览器 NFT 列表 / Transfer 日志
        确认后逐枚 safeTransferFrom，同钱包串行

原生币钱包（mint_engine/treasury + run_registry）：
        一对多：预览随机金额，总量 gate；执行带 execute_plan + preview_source_address
        多对一：预览 fixed/all，并发归集
        私钥一行一个查余额；分发源仅用第一行
        长任务经 run_registry：client_id 单 active、心跳、cancel、live_events 轮询

RPC 429
        → retry

nonce too low
        → refresh nonce

NotActive
        → wait

InvalidProof
        → no retry

AlreadyMinted
        → 该钱包结束，不停其他钱包

Insufficient ETH
        → 分析标红；当前启动仍会尝试发送

SoldOut
        → SKIP 尚未广播的钱包；已发出的仍等回执
```

# 49. 核心结论

真正的“通用 Mint Bot”不是：

```text
通用 ERC-20 mint()
通用 NFT mint()
```

而是：

```text
                  Generic Mint Engine
                         │
          ┌──────────────┼──────────────┐
          │              │              │
       Discovery       Adapter       Transaction
          │              │              │
      ABI/Selector    SeaDrop        Build
      Proxy           Merkle         Sign
      Bytecode        Signature      Broadcast
      Heuristic       Direct         Receipt
                     ERC721
                     ERC1155
                     ERC20
```

其中：

```text
Discovery
```

回答：

> “这个合约怎么 Mint？”

```text
Adapter
```

回答：

> “这个 Mint 模式具体需要什么参数？”

```text
Transaction Engine
```

回答：

> “如何正确、快速地把交易发送到链上？”

这样以后增加新的 NFT 项目、新的 Mint Protocol、新的 Chain、新的 Mint 方式时，不需要重写整个机器人，只需要新增对应 Adapter、Selector 或 Parameter Resolver。
